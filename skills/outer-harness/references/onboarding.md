# Conversational onboarding

Start with explanation and questions, not installations. Establish whether the user wants evaluation, setup, or migration. Reading this repository does not authorize account connections, writes or schedules.

1. Explain the operating loop using one practical example from the user's stated needs. Separate reusable procedures, their private setup, connected tools, and optional scheduled work. Describe actual limitations without presenting experimental runtime behavior as established.
2. Ask one or two practical questions at a time. Learn which ongoing matters need continuity, where the user already keeps records, what should remain private, what maintenance is welcome, and which actions always need approval. Reuse supplied answers. Do not transfer another user's preferences, accounts, project structure or notification load.
3. Propose Adopt now / Later / Omit, tied to the user's examples. Prefer native features and existing connected tools; identify setup and privacy costs. No project management, automation, coding repository or separate Google account is compulsory. Roles can share an application; generic role support does not prove every provider works.
4. After the user approves the setup, agree one private authoritative setup-record location. Record source-role mappings, scopes and permissions in the configuration format documented by the core skill. Keep unknowns explicit. Existing users keep their current config_locator unless migration is separately approved. Creating this setup record is itself a write: perform it only under that explicit approval and verify readback.
5. Independently verify service access, installation/native readability and the standing locator in the surfaces the user will actually use. Use supported tools; report a specific unavailable operation rather than inventing successful installation or account-level instructions. Repository inspection is not installation.
6. Test a read-only question whose correct source and expected answer the user can check. Identify records actually read, distinguish private versus shared scope, and leave unrelated systems untouched. Do not test another person's private account.
7. After separate explicit approval, test a harmless reversible update to a user-approved test record. Capture the previous value, read back the change, restore and verify when that restoration was included in the approval. Do not manufacture an operational event or imply it was real work. Verify a repeat and required-source-failure case without harmful mutations.
8. Discuss schedules only after the relevant read/write path works. Choose none or one useful workflow initially. Inspect existing registrations before proposing another; retain their settings and independence. Installing a skill or creating a profile does not schedule anything.

End each setup stage with the smallest useful summary: decided, actually verified, still pending, and the next question/action. Do not present a giant questionnaire or require users to understand hashes, packaging or backend architecture. Do not claim automatic activation or device parity without separate observed evidence.
