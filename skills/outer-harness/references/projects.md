# Project workflows

## Shared requirements
Read the configuration and relevant current project/access policies before dependent work. Resolve the owning source by role and explicit project scope. Use current delivery mappings rather than older provider-specific wording. Missing access to the owner is a blocker, not permission to mirror task state elsewhere.

Read a relevant operational record only when current state is needed, a project-state question was asked, or a material update needs a safe merge. Resumed implementation/document work alone does not require a project-manager read. Whole-portfolio reads belong only to daily or explicitly requested portfolio reviews. Completion and email workflows remain bounded. No relevant candidate means no project read/write.

Search before creating. Classify NEW, UPDATE, ADVANCE, BLOCKED, DONE, DECISION, STALE, UNCERTAIN or NO CHANGE. Recency is not importance; silence is not completion; STALE does not authorize deletion. With explicit maintenance permission, reconcile clear low-risk changes, preserve unique context/source links, and read changed records back. Do not invent dates, outcomes, commitments or chat URLs.

Keep each changing task in one owner. Update a portfolio pointer for a delivery project only when portfolio outcome, priority, personal decision or commitment materially changes. Preserve detailed task relationships in the delivery system and evidence in its source. Keep routine domain records out of project managers.

## Reconcile
Use the current interactive request's scope. Update only material state changes at a meaningful stopping point; promptly preserve important blockers/commitments. Do not expand a targeted update into a portfolio review.

## Daily
Read the portfolio once with required pagination, then follow configured pointers to bounded relevant delivery state. Reuse the result for reporting. Reconcile evidence before considering priorities, WIP, dependencies and the rolling roadmap. Cover the user's meaningful domains, not only recent or technical work. Count each mapped outcome once.

Use current policy's WIP and review rules; distinguish forecasts from commitments. Consider a small number of leverage points rather than scoring the entire backlog. Follow a weekly/deeper/public-presence review only if configured. Propose public changes under the user's writing and publication boundaries; do not publish them automatically.

Preserve the exact task-specific briefing scope, reporting threshold and deduplication rules. A consolidated exception-only morning brief stays one final brief; do not restore a separate Focus/Roadmap report, progress messages, routine successes or all-clear messages. Other approved operating checks in that task remain intact; this workflow does not replace them.

Do not duplicate event routing or completion watches. Read email only under the existing specific expected-message/stale-dependency recovery exception, not a general inbox sweep. A scheduled review does not authorize starting substantive implementation or consequential actions.

## Completion watch
Start from relevant tracked expectations already due: a delivery, appointment, arrival, deployment, automation execution or dated milestone. Use known record/source pointers, then bounded owner-specific discovery only when necessary. Never scan the whole portfolio/workspace as fallback or broadly reprioritize here.

Verify actual result evidence before advancing a gate. An accepted run request is not completed execution. Treat explicit DTSTART timezone correctly; use task default timezone when DTSTART has none, never assume UTC. Ask about unverifiable offline outcomes without treating no reply as failure/completion. Preserve the existing alert threshold and silence/deduplication behavior.

## Email event
Fetch the actual incoming message/thread in the configured assistant account. Ignore sent mail, drafts, spam, trash and noise. Establish operational significance before project access. Match by exact message/thread/project pointer, then known correspondent with context, then bounded high-confidence discovery. Report important ambiguity rather than guessing.

Classify EXISTING_PROJECT_UPDATE, WAITING_RESOLVED, DECISION_OR_ACTION_REQUIRED, ARTIFACT_RECEIVED, CONFIRMED_SCHEDULED_COMMITMENT, POSSIBLE_NEW_WORK or NO_OPERATIONAL_SIGNIFICANCE. Make only permitted low-risk updates to the owner with source links and readback. Move Waiting to the configured ready state only when an external dependency clearly cleared and the next action belongs to the user.

Deduplicate by incoming message ID, not thread. Track verified effects separately: successful record updates must not suppress still-required decision alerts. After partial success retry only pending effects; do not mark the whole event processed until intended effects are verified. Important new quotes or proposed appointments retain their task-specific user-facing alert even if the state update succeeded.

Record an already-authorized unambiguous confirmed commitment only under the configured calendar permission and policy. Check duplicates, exact date/time, organizer and attendees, including workday/weekend rules. Proposed times do not authorize booking. Do not auto-reply, approve quotes, negotiate, accept terms, purchase, cancel/reschedule or create substantive work from unsolicited mail.

Follow the existing event registration and transport. This reference does not create a webhook or authorize conversion to polling.
