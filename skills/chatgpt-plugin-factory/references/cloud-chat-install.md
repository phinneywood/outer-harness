# Release a personal skill to ordinary Chat

Use this path when fresh ordinary Chat must discover and read a skill. A personal skill saved to the managed skills checkout may load in Work yet remain unavailable to ordinary Chat. Its cloud plugin is a separate installed release; edits to source do not update it automatically.

1. Resolve the existing personal skill by frontmatter `name`. Read the skill-creator instructions, edit and validate the skill in the managed personal-skills checkout, and save that one skill. Retain its installed identity. Pin the reconciled source revision and hashes before packaging.
2. Make a skills-only plugin archive with `plugin.json` at the ZIP root and `skills/<name>/SKILL.md` plus only the required resources. The accepted `pocock-handoff` archive used a semantic `version`, `description`, `author.name`, and `extensions.com.openai.interface` containing `displayName`, `shortDescription`, `longDescription`, `developerName`, `category`, and `capabilities`. Check the current official schema and uploader feedback for the target. Keep required instructions self-contained in `SKILL.md`: a bundled sibling `HOST.md` was not readable through ordinary Chat's skill reader in the 2026-09-27 test.
3. Inspect the actual archive entries and compare `SKILL.md` bytes or hashes with the pinned source. Run the host skill validator and the static package checker. A valid ZIP proves neither installation nor Chat loading.
4. In ChatGPT **Plugins → Personal → Add → Upload plugin archive**, upload the ZIP and then select **Install plugin** on the created plugin. For a subsequent release, increment the plugin version and use the plugin detail page's **More actions → Upload new version**. Confirm the installed version. A source update alone does not deploy the new ZIP.
5. Start a fresh **ordinary Chat** conversation with no copied instructions or attached package. Ask it to discover the installed skill and read `SKILL.md` using its native reader. Require a tool result and a distinctive instruction from the installed version that was absent from the prompt. If the needed resource cannot be read, repair the package/instructions and repeat the release. Test iOS in a separate fresh iOS conversation before claiming iOS support.
6. Record the source revision and hash, archive version and manifest, installed cloud plugin version, fresh Chat URL, native reader result, behavior test, and host-specific limits in the release record. Avoid two enabled copies with the same skill name when checking which installation is active.

For a growing collection, group closely related skills in one plugin when they share an audience and release cadence. Keep unrelated skills separate. Version every upload and test each skill from a fresh target conversation. A GitHub repository can hold canonical source, but it does not replace cloud upload, installation, or runtime verification. Review files for secrets and personal data before making that repository public.
